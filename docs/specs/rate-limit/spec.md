# 分布式限流（令牌桶 + Redis 滑动窗口）Spec

## 背景

- 项目已有鉴权中间件（`AuthMiddleware`），受保护接口（上传、删除、点赞等）按用户 ID 鉴权，但**无任何限流防护**。
- 高并发下，单个用户或脚本可高频调用受保护接口，造成后端压力或刷量。
- 已有 `core.Redis`（go-redis v9）可支撑分布式限流；`internal/middlewares` 现仅含 auth/cors/requestid。
- 项目可水平扩容：单机限流与分布式限流在多实例下的语义差异需要被正确实现并讲清。

## 目标

- 提供两种限流算法：**内存令牌桶**（单机）、**Redis Lua 滑动窗口**（分布式）。
- 通过**一个中间件**对登录后接口按**用户 ID** 限流，算法可配置切换。
- 超限返回 429 与标准限流响应头；Redis 不可用时安全降级。

## 功能需求

- **F1（限流器接口）**：定义一个统一的「是否放行」判定接口，两种算法都实现它，使中间件对算法无感知。

- **F2（内存令牌桶，单机）**：进程内令牌桶——以固定速率补充令牌、桶有容量上限；每次请求消耗一个令牌，令牌不足则拒绝。**多实例各自维护独立桶**（单机语义）。

- **F3（Redis 滑动窗口，分布式）**：基于 Redis ZSet 的滑动窗口——以当前时间戳为 score 记录请求，仅统计窗口内的请求数，超限拒绝；所有操作在一个 **Lua 脚本**内原子完成，保证并发下计数准确。**跨实例共享同一窗口**（分布式语义）。

- **F4（限流中间件）**：一个中间件，从配置读取算法与阈值，构造对应限流器；以**用户 ID** 为限流 key；挂载在受保护路由组（鉴权之后）。

- **F5（超限响应）**：被拒绝时返回 HTTP 429，并携带 `Retry-After` 与 `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset` 响应头。

- **F6（Redis 降级）**：滑动窗口依赖 Redis；Redis 不可用时**放行（fail-open）**，避免限流组件本身造成服务不可用，并记录告警日志。

## 非功能需求

- **N1**：不改变现有接口的正常响应契约（仅在超限时新增 429）。
- **N2**：单机/分布式两种语义在文档与日志中明确区分，便于讲清多实例差异。
- **N3**：限流算法、阈值、窗口均可配置，零值套默认值。
- **N4**：自实现两种算法（不引入限流框架），Lua 脚本原子执行，无第三方限流依赖。
- **N5**：结构化日志——触发限流时记录用户、算法、剩余量。

## 不做的事

- 不做公开接口（未登录）的限流（按 IP 的维度留待后续）。
- 不做按接口路径细分的不同阈值（全局统一一套阈值，per-route 阈值留待后续）。
- 不做分布式令牌桶 / 漏桶算法（令牌桶明确为单机实现）。
- 不引入 `golang.org/x/time/rate` 等限流库。

## 验收标准

- **AC1（F1/F4）**：受保护接口挂载中间件后，超过阈值的请求返回 429。
- **AC2（F2）**：令牌桶配置 rate=N、burst=B 时，突发 B 个请求放行，第 B+1 个被拒绝；等待补充后恢复放行。
- **AC3（F3）**：滑动窗口配置 window=W、limit=L 时，窗口内第 L+1 个请求被拒绝；窗口滑过后恢复。
- **AC4（F5）**：429 响应包含 `Retry-After` 与 `X-RateLimit-*` 头。
- **AC5（F6）**：Redis 不可用时滑动窗口限流放行（不返回 429）。
- **AC6（F3）**：并发请求下窗口计数不超限（Lua 原子性）。
