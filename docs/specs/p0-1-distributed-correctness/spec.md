# Vistack P0-1 分布式正确性加固 Spec

## 背景

Vistack 已是三角色（api / worker / transcoder）分布式骨架，但多副本部署时存在四类正确性问题：

1. **单例任务重复运行**：转码重试派发器（dispatcher）与转码看门狗（watchdog）在**每个** worker 实例启动时都会运行。worker 一扩容，多个实例同时扫描 Redis ZSet 与数据库，导致重试消息被重复投递、任务状态被重复触碰。
2. **迁移竞争**：每个 api 实例启动时都执行数据库自动迁移（AutoMigrate），多副本同时建表/加列会互相竞争、偶发失败。
3. **消费并发为 1**：Kafka 消费者是单 goroutine 顺序循环（读一条 → 处理 → 提交），而转码 gRPC 调用是阻塞的，单个 worker 同时只能转码一个视频，无法通过增加副本以外的方式提升吞吐。
4. **无优雅停机**：worker 进程以 `select {}` 永久阻塞、不处理信号；api 直接 `r.Run()` 阻塞。滚动发布时进程被直接杀死，在途请求被掐断、Kafka 消费者组 rebalance 引发消息延迟与重复。

## 目标

- 让 worker 多副本（如 `--scale worker=3`）运行下：单例任务全局只运行一份，无重复投递。
- 滚动发布（SIGTERM）时：worker 排空在途任务后退出、消费者组平滑交接；api 排空在途请求后退出。
- 单个 worker 实例可并发处理多个转码任务，吞吐不再受"一个实例一个任务"限制。

## 功能需求

- **F1（单例调度）**：转码重试派发器与转码看门狗在任何时刻全局只在一个 worker 实例上运行；leader 实例故障时自动转移给其他实例，无主窗口不超过租约 TTL；领导权丢失时对应循环停止，不产生分裂（两个实例同时执行）。
- **F2（worker 优雅停机）**：worker 收到 SIGTERM/SIGINT 后依次执行：停止接收新消息 → 等待在途任务完成（有超时上限）→ 退出；超过超时上限后强制退出，不得无限挂起。
- **F3（api 优雅停机）**：api 收到 SIGTERM/SIGINT 后：停止接收新请求 → 等待在途请求完成（有超时上限）→ 退出。
- **F4（迁移独立执行）**：数据库自动迁移不再由 api 实例启动时竞争执行；提供独立入口执行迁移；应用启动时不再隐式迁移。
- **F5（并发消费）**：Kafka 消费者支持并发处理：同一 worker 内多个消息可并行处理；消息处理成功后再提交 offset（至少一次语义）；配合既有 Redis 租约与数据库状态机保持幂等，同一任务不会被重复执行。

## 非功能需求

- **N1（配置向后兼容）**：新增配置项均有默认值，旧配置文件不报错即可运行。
- **N2（依赖降级）**：etcd 不可用时 worker 仍能启动运行，单例任务按降级策略处理（记录告警或退化为单实例模式），不影响既有转码消费。
- **N3（幂等保持）**：并发消费不得破坏现有幂等保证（Redis SetNX 租约 + 数据库状态前置校验）。
- **N4（代码组织）**：遵循现有 `internal/` 分层（role / core / message_queue），新增代码不破坏三角色职责边界。
- **N5（编译与测试）**：全项目 `go build ./...` 通过，改动模块有针对性测试或验证命令。

## 不做的事

- 中间件高可用（PostgreSQL / Redis / Kafka / MinIO / etcd 集群化）——属 P1 阶段。
- 可观测性（Prometheus metrics / OpenTelemetry 链路 / 日志聚合）——属 P1 阶段。
- gRPC mTLS、etcd/Kafka 加密认证——属 P2 阶段。
- etcd 配置中心、分布式锁、节点 ID 分配、特性开关——属 P2 阶段。
- Kafka 消息契约版本化、DLQ、Outbox——属 P0-2 阶段。

## 验收标准

- **AC1（对应 F1）**：启动 3 个 worker 副本，观察 etcd 选举 key 与日志：任意时刻只有 1 个实例执行 dispatcher/watchdog；杀掉 leader 实例后，另一个实例在约一个租约 TTL 内接任并恢复执行。
- **AC2（对应 F2）**：向 worker 发送 SIGTERM，观察日志顺序：停止接收 → 排空在途 → 退出；期间 Kafka 消费者组完成 rebalance，其他 worker 继续消费，无重复执行（幂等由租约+状态机保证）。
- **AC3（对应 F3）**：向 api 发送 SIGTERM，在途请求正常返回（可观察访问日志与退出码），进程在超时上限内退出。
- **AC4（对应 F4）**：api 启动日志中不再出现 AutoMigrate 执行；通过独立迁移入口执行迁移成功并可重复执行（幂等）。
- **AC5（对应 F5）**：配置并发数 > 1 时，单个 worker 可同时处理多个转码任务（观察并发处理日志）；并发数可配置且默认值合理。
