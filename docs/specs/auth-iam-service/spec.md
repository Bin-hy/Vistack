# Auth/IAM 服务拆分 Spec

## 背景

当前认证逻辑全部耦合在 api 服务内：

- `UserApi.Login/Register` 直接访问数据库完成登录、注册、用户资料读写。
- `TokenManager` 使用 **HS256 对称签名**，签发与验签共享同一个 secret；`Claims` 仅含 `user_id` 与 `exp`。
- `AuthMiddleware` 只做签名与过期校验，无授权（RBAC）逻辑。
- 用户数据（`users` / `user_profiles`）与视频业务共用同一服务、同一数据库，认证与业务边界不清。
- RBAC 仅有数据模型（role/authority），README 声称的细粒度授权实际未实现。

拆分的动机：认证是安全敏感、发布频率相对独立、需要单独密钥治理的边界；HS256 共享 secret 意味着任何持密钥的服务都能伪造 token，无法满足"拆出后安全隔离"的目标。

## 目标

- 将认证与身份（Auth/IAM）拆分为**独立服务**（独立进程、独立部署、独立扩容）。
- 签名由 HS256 对称升级为 **RS256 非对称 + JWKS 公钥分发**，消费方本地验签、不依赖中心、不持有私钥。
- 用户域（`users` + `user_profiles`）整体归属 auth 服务，业务侧仅通过 userID 引用。

## 功能需求

- **F1（认证服务独立）**：提供登录、注册、密码修改、用户信息查询的独立服务；api 不再承载认证与用户资料逻辑。
- **F2（RS256 签发）**：登录成功后签发 RS256 签名的 JWT，claims 至少包含 `user_id`、`exp`；私钥仅 auth 服务持有。
- **F3（JWKS 公钥分发）**：auth 暴露 JWKS 端点（或等价公钥分发方式），消费方据此验签。
- **F4（本地验签）**：api 的认证中间件改为从 JWKS 获取公钥本地验签，验签过程不回调 auth 服务；验签失败返回 401。
- **F5（用户数据归属）**：`users`/`user_profiles` 的读写归属 auth；api 通过 userID 引用用户，视频作者等展示信息通过调用 auth 提供的用户查询接口获取，不再直接 join 用户表。
- **F6（注册/登录行为保持）**：现有注册（用户名/昵称/邮箱唯一性校验、默认角色、密码哈希）与登录（校验密码、返回 token 与用户信息）行为不变。
- **F7（路径兼容）**：对外认证路径（`/api/v1/auth/*`）保持不变，前端无需改动即可通过网关/路由把认证请求转发到 auth 服务。

## 非功能需求

- **N1（密钥安全）**：私钥不入库、不入镜像、不进配置文件明文，通过环境/Secret 注入。
- **N2（密钥轮换）**：支持私钥轮换（新旧并存验证），轮换不导致在途 token 立即失效。
- **N3（无状态水平扩展）**：auth 服务无会话状态，可多副本部署、独立扩容。
- **N4（配置向后兼容）**：新增配置项均有默认值，旧配置不报错即可运行。
- **N5（编译与测试）**：全项目 `go build ./...` 通过。

## 不做的事

- RBAC 授权校验（role/authority 拦截中间件、角色管理 API）——本次不做，仅数据模型保留。
- refresh token / token 撤销 / 黑名单——本次不做。
- SSO / OAuth / 多租户——本次不做。
- API 网关统一入口、限流——本次不做（部署层面，可后续）。
- 用户变更事件同步与本地缓存——本次不做（视频作者信息直接调用 auth 接口获取）。

## 验收标准

- **AC1（对应 F1）**：auth 作为独立角色可单独启动；登录/注册经 auth 接口完成，api 不再处理认证请求。
- **AC2（对应 F2/F3）**：登录返回的 token 为 RS256 签名；auth 暴露 JWKS 端点且能返回公钥。
- **AC3（对应 F4）**：api 不持有私钥、不回调 auth 即可验签 token；错误 token 返回 401。
- **AC4（对应 F5）**：api 代码中不再出现对 `users`/`user_profiles` 的 join/Preload 查询；作者信息改为经 auth 接口获取。
- **AC5（对应 F6）**：现有登录/注册端到端可用（注册 → 登录拿 token → 携带 token 访问受保护接口）。
- **AC6（对应 F7）**：`/api/v1/auth/login` 与 `/api/v1/auth/register` 路径与响应结构不变，前端零改动即可工作。
